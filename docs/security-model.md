# Security model

PRAMAAN aims for **tamper evidence and defence in depth**, not absolute security. This page lists what
each mechanism does and — equally important — what it does not do.

## Cryptographic primitives (standard libraries only)

| Purpose | Primitive | Library |
|---|---|---|
| Event / manifest / file integrity | SHA-256 | `@noble/hashes` (shared code), `node:crypto`, `java.security.MessageDigest` |
| Canonical serialisation | RFC 8785-compatible subset (ADR-002) | `packages/event-contracts/src/canonical.ts` |
| Device event signatures | ECDSA P-256 / SHA-256 (DER) | Android Keystore (`SHA256withECDSA`), verified with `node:crypto.verify` |
| Biometric attestation | auth-per-use EC P-256 key + `BiometricPrompt.CryptoObject` | AndroidX Biometric 1.1 |
| Local database | SQLCipher (AES-256) | `@op-engineering/op-sqlite` with `"sqlcipher": true` |
| Evidence files & observation buffer at rest | AES-256-GCM (Keystore key, random 96-bit IV) | `javax.crypto` |
| Passwords | Argon2id (m = 19 MiB, t = 2, p = 1) | `@node-rs/argon2` |
| Access tokens | HS256 JWT, 15 min | `jose` |
| Refresh tokens | 256-bit random, SHA-256 stored, rotation + reuse detection | `node:crypto` |
| Identifiers / challenges | UUIDv4 and 3-digit codes from a CSPRNG with rejection sampling | `crypto.getRandomValues` (SecureRandom on Android) |
| Transport | TLS (Render-managed HTTPS); cleartext blocked in release builds | Android network security config |

## Integrity is not authenticity

- **Integrity**: the bytes have not changed since they were hashed/signed. PRAMAAN verifies this on the
  server (recomputing SHA-256 of received bytes, never trusting a client hash), on every retrieval and
  export, and offline with the verifier.
- **Authenticity of the event source**: the event was signed by the private key registered for that
  device and approved by an administrator.
- **Not proven**: that the photograph shows a real scene (and not a screen or print), that the time or
  location reported by the phone is true, or that the person holding the phone is the officer. A
  modified or rooted client can compute valid hashes over fabricated data and sign them with the
  device key it controls.

## Key management

| Topic | Design |
|---|---|
| Device key generation | On first registration, inside Android Keystore (StrongBox if `FEATURE_STRONGBOX_KEYSTORE`, else TEE); non-exportable. Hardware backing is reported (`KeyInfo.securityLevel`) and shown to the administrator. |
| Public-key registration | `POST /devices/register` (officer session) → `PENDING`; admin compares the SHA-256 fingerprint shown on the phone, then approves. |
| Rotation | Register a new device ID with a new key, revoke the old one. Events signed by the old key remain verifiable against the stored public key. |
| Revocation / lost device | Admin revokes → further batches rejected (`DEVICE_REVOKED`), refresh tokens of that device revoked, flag + audit record created. Already accepted events are retained. |
| Reinstall / device replacement | Keystore keys are destroyed on uninstall → new registration; the old device ID cannot be re-registered with a different key (409). |
| Server signing keys | None. The server does not sign receipts (future work: signed sync receipts). |
| Local DB key | 256-bit random, wrapped with a Keystore AES-GCM key, stored in private SharedPreferences, decrypted at start-up into process memory. Never in source control, never universal. |
| Backup / recovery | `allowBackup=false` and backup/data-extraction exclusions: keys, ledger and evidence are not backed up. If the Keystore key is lost (app data cleared, OS reset), **unsynchronised local data is unrecoverable** — by design. |
| Server secrets | `JWT_ACCESS_SECRET` generated by Render (`generateValue`) or locally; the API refuses placeholder-looking secrets in production. |

## Ledger limitations and anchoring
A hash chain provides tamper *evidence* only relative to something trusted. The server stores the last
verified `(sequence, hash)` per device (`device_chain_heads`) and returns it in every sync response; the
device records it (`sync_cursors.server_chain_head`). Any later rewrite of acknowledged history is
detected (link mismatch, sequence conflict). **Residual risk:** events that were created and rewritten
entirely on a compromised device *before* their first synchronisation cannot be distinguished from
genuine ones. The server audit log is likewise hash-linked; its checkpoint (`GET /audit-events/checkpoint`)
should be recorded outside the system (e.g. in the duty register) to detect rewriting by a privileged
database user (demonstrated in `domain.test.ts`).

## Device integrity checks (heuristic, bypassable)
Recorded in every manifest and in `DEVICE_INTEGRITY_OBSERVED`: debuggable build, `su` paths and Magisk
directories, `test-keys` build tags, attached debugger, developer options, ADB, emulator fingerprints,
APK signing-certificate SHA-256, hardware-backed key. Play Integrity is an **optional, disabled-by-default
adapter** (`playIntegrityVerdict: null`): enabling it needs a Google Cloud project, the Play Integrity API
and server-side token decryption, none of which is configured here. No verdict is ever fabricated.

## Network and API hardening
HTTPS in production (Render), HSTS, Helmet security headers with a `default-src 'none'` CSP for the API,
CORS allowlist (production rejects `*` and localhost), JSON size limit 2 MiB, evidence limit 8 MiB with
streaming hashing, request/response timeouts, three rate limiters (login per IP+e-mail, sync, general),
structured pino logs with redaction of authorisation headers, cookies, passwords and tokens, generic error
messages with request IDs, parameterised SQL only, object-level authorisation for officer-scoped records,
and secure defaults validated at start-up (`config/env.ts`). Least-privilege database roles are
recommended in `database/README.md`.
